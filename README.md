# docpipe

[![CI](https://github.com/Bahakirbasogluu/document-extraction-pipeline/actions/workflows/ci.yml/badge.svg)](https://github.com/Bahakirbasogluu/document-extraction-pipeline/actions/workflows/ci.yml)

A schema-driven document extraction pipeline. It takes scanned business documents (invoices, delivery notes, insurance policies), splits bundles into single documents, classifies each one, extracts its fields into a typed schema, checks them against business rules and maps the accepted ones to the record a downstream system expects. Documents that fail a rule go to review with the reason attached.

The design comes from document-processing systems I have built for accounting and logistics teams. The code here is written from scratch and runs on synthetic documents; it contains no client code or data.

```
file -> read -> split -> classify -> extract -> validate -> map -> record
         OCR    bundle    type       schema     rules             or review
```

## What it shows

- **One schema per document type.** A Pydantic model is the contract between the extractor, the validation rules and the mapper. The same model is passed to the LLM as the structured-output schema.
- **Extraction and judgement are separate.** The extractor copies what is printed and never computes or corrects a value. Validation then decides whether the document is consistent. An extractor that "fixes" a wrong total hides exactly the documents a person needs to see.
- **Every stage is an interface.** OCR, classification and extraction can each be replaced without touching the rest. Two backends are included: a rule-based one that runs offline, and an Azure one (Azure AI Document Intelligence for OCR, Azure OpenAI structured outputs for classification and extraction).
- **Review is an outcome, not an exception.** A result is `accepted` with a mapped record, `needs_review` with a list of issues that name the field and the rule, or `unsupported`.
- **Measured against labelled documents.** `docpipe eval` reports splitting, classification and field-level accuracy, and how many faulty and clean documents ended up in review.

## Quick start

```bash
pip install -e ".[dev]"
docpipe run samples/docs/invoice_12.txt
docpipe eval
pytest
```

`docpipe run` prints one JSON object per document found in the file. `invoice_12.txt` carries a tax number with a wrong check digit:

```json
{
  "source": "invoice_12.txt",
  "pages": [1],
  "doc_type": "invoice",
  "confidence": 1.0,
  "status": "needs_review",
  "record": null,
  "issues": [
    {"code": "invalid_tax_id", "severity": "error", "field": "supplier_tax_id",
     "message": "supplier tax number fails its check digit"}
  ]
}
```

(`data`, the extracted fields, is omitted here for length.)

## Results on the bundled samples

`samples/` holds 38 files with 45 documents in Turkish and English, generated by `samples/generate.py` with a fixed seed. They vary in label wording, number and date formats and layout. Five invoices span two pages, five files are bundles of two or three documents, four files are not a supported type, and six documents carry a deliberate fault.

Rule-based backend, `docpipe eval`:

| Measure | Result |
| --- | --- |
| Files split into the right number of documents | 38 / 38 |
| Documents classified correctly | 44 / 45 (97.8%) |
| Fields extracted correctly | 335 / 387 (86.6%) |
| Invoice fields | 200 / 240 (83.3%) |
| Delivery note fields | 84 / 91 (92.3%) |
| Insurance policy fields | 51 / 56 (91.1%) |
| Faulty documents sent to review | 6 / 6 |
| ... of which the report names the fault | 3 / 6 |
| Clean documents accepted without review | 15 / 35 |

How to read this:

- The rule-based extractor only finds a value that follows a label it knows on the same line. The generator deliberately uses unknown labels and next-line values in part of the documents, which is where the missed fields come from. This backend is the baseline, not the goal.
- The misclassified document is a payment reminder that mentions an invoice number and a due date. The keyword classifier calls it an invoice; it then fails validation and goes to review.
- No faulty document was accepted, but only three of the six were stopped by the rule that matches their fault. The other three, all invoices whose totals do not add up, were stopped because the extractor missed one of the amounts, so the totals rule had nothing to compare. A missing required field blocks a document for that reason.
- 20 clean documents went to review because a required field was missed. For a posting workflow that is the right direction to fail in, and the 15 / 35 straight-through rate is the number a better extractor should raise.
- The LLM backend goes through the same pipeline; the test suite drives it with a model stub that returns schema-valid answers.

The samples are synthetic; the numbers describe how the pipeline behaves on them.

## Using the Azure backend

```bash
pip install -e ".[azure]"
cp .env.example .env   # fill in the endpoints, keys and deployment name, then export them
docpipe --backend azure run invoice.txt
```

To read PDFs or images, pass the OCR reader when building the pipeline:

```python
from docpipe import Pipeline
from docpipe.classify import LLMClassifier
from docpipe.extract import LLMExtractor
from docpipe.llm import AzureOpenAIModel
from docpipe.readers.azure_di import AzureDocumentIntelligenceReader

model = AzureOpenAIModel()
pipeline = Pipeline(
    reader=AzureDocumentIntelligenceReader(),
    classifier=LLMClassifier(model),
    extractor=LLMExtractor(model),
)
for result in pipeline.run("scan.pdf"):
    print(result.status, [issue.code for issue in result.issues])
```

Any model that can fill a Pydantic schema works: implement `parse(system, user, schema)` from `docpipe/llm.py`.

## Adding a document type

1. Add a schema in `src/docpipe/schemas/` and register it in `SCHEMAS`.
2. Add its title and body keywords in `classify/keywords.py` (and to the `Literal` in `classify/llm.py`).
3. Add its required fields and rules in `validate.py`.
4. Add a mapper in `mapping.py`.
5. For the rule-based backend, add its labels in `extract/rules.py`.

## Layout

```
src/docpipe/
  models.py          Page, Segment, Issue, DocumentResult
  schemas/           one Pydantic model per document type
  readers/           text files, Azure AI Document Intelligence
  split.py           bundle -> documents
  classify/          keyword classifier, LLM classifier
  extract/           rule-based extractor, LLM extractor
  parsing.py         numbers, dates, currencies, tax number check digit
  validate.py        required fields and business rules
  mapping.py         schema -> downstream record
  pipeline.py        the stages wired together
  evaluate.py        scoring against labelled documents
  cli.py             docpipe run / docpipe eval
samples/             generator, documents, labels
tests/
```

## Validation rules

| Type | Rule | Code |
| --- | --- | --- |
| All | A required field is missing | `missing_field` |
| Invoice | Net + VAT differs from gross | `totals_mismatch` |
| Invoice | VAT rate times net differs from the VAT amount | `vat_mismatch` |
| Invoice | Line amounts do not add up to net | `lines_mismatch` |
| Invoice | Quantity times unit price differs from a line amount | `line_amount_mismatch` |
| Invoice | Due date before issue date | `due_before_issue` |
| Invoice | Supplier tax number fails its check digit | `invalid_tax_id` |
| Delivery note | No items | `no_items` |
| Insurance policy | End date not after start date | `invalid_period` |
| Insurance policy | Premium not positive | `invalid_premium` |

Amounts are compared with a tolerance of 0.02. Two rules are warnings and do not block a document: an invoice without line items and a delivery note without a plate.
